# ordi v1.7.0

The MCP tool catalog learns to answer its own first question: "which id?"

## Agents can discover ids now

Every project and company tool - `get_project_status`,
`get_project_profitability`, `get_company_overview`, `list_unbilled_time`,
`create_invoice_from_time` and the rest - takes a `projectId` or `companyId`.
Until now no tool produced those ids: an agent could work with a project only
if it already knew the project, and the only accidental way in was a task in
`list_my_tasks` happening to carry its project id. An empty task list meant a
dead end.

Two new tools close the loop:

- **`list_projects`** - every project the token's owner can access, with
  `status` and `companyId` filters. The same permission filtering as the web
  app: a token without access to a project does not see it.
- **`list_companies`** - CRM companies with name-substring search (`q`),
  `status` filter and paging.

Both return compact rows (id, key/name, status, dates, owner) instead of raw
table rows.

## Search finds projects

Global search covered companies, tasks, invoices and KB pages - projects were
simply absent. Searching the name of a project you could open in the browser
returned nothing. The projects section is there now: name or key match,
key-matches ranked first, capped and permission-filtered like every other
section. The `search` tool description also says honestly what it matches
(names, titles, numbers - not arbitrary fields) and points agents at the list
tools for enumeration.

## Tool responses are scrubbed

MCP tools used to return whatever the REST endpoint returned - full database
rows, `version` counters, `deletedAt: null`, `templateSourceId` and all. Now
every tool response is recursively scrubbed before it reaches the model. Less
noise in the agent's context, and one strictly-worse leak closed: the raw
company row contains `portalToken`, the secret that grants access to that
client's portal. It never belonged in a model's context window, and it can no
longer get there.

## For self-hosters behind Cloudflare

Found live while debugging "Authorization with the MCP server failed": new
Cloudflare zones ship with the managed **"Block AI bots"** rule enabled, and
it 403s Claude's MCP traffic (user agent `Claude-User`) on `/api/v1/mcp`
while letting the OAuth handshake through - so authorization succeeds and
the connection then dies. If that is your symptom, check Security → Events
for `ai-bots-block` matches and either disable the rule for the zone or
allow `Claude-User` in AI Crawl Control. Nothing in ordi can fix this from
the origin side; the block happens before the request reaches it.
