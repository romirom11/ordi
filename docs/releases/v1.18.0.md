# ordi v1.18.0

v1.17.0 made the CRM workable one lead at a time. This release makes it
workable fifty at a time, and teaches it to answer the question every founder
asks on Friday: how are we actually doing?

On the projects side, the theme is finishing what the API had already earned.
Intake requests, cycle completion, task templates and recurring rules were all
fully implemented server-side and reachable from nowhere: a request submitted
through the public form landed in a table no screen ever read. Those screens
exist now. And moving a task between projects stops quietly losing its
history.

## Leads in volume

The lead table grows a select column and a bulk bar: pick up to 200 leads and
reassign the owner or move the status in one action. Every lead still goes
through the single-lead rules, so a bulk disqualification cancels planned
activities and stops sequences exactly as one-at-a-time work does, a nurture
batch demands a return date, and converted leads refuse to be rewritten.
Failures are reported per lead instead of aborting the batch.

Lead lists come in and go out as CSV. The importer takes the shape a research
batch actually has (`companyName,title,product,status,score,signal,sourceUrl,
suggestedChannel,opener`), creates unknown companies as prospects on the fly
so a list does not require a company import first, validates line by line with
a dry run, and hands ownership to the importer. `/export/leads.csv` joins the
company and owner names in.

The table also stops lying about its size: it is bounded at 200, and when
there are more leads than that it says so, the same honesty the pipeline board
already had.

## The CRM answers "how are we doing"

A new Analytics tab: the lead funnel by status, lead intake over the last 30
days against the 30 before, lead-to-deal conversion among leads that reached
an outcome, pipeline value by stage (raw and weighted by stage probability),
win rate, won value, and the reasons deals are lost, ranked. Every figure is a
live snapshot of the base tables; nothing is computed from a column that does
not exist. Roles without `deals.read` get the lead half only.

## Requests reach the team

The public intake form existed; the queue behind it did not. Projects get an
Intake tab, with a pending count on the tab itself, where each request is
accepted into a task (pick status and assignee; the requester is mailed) or
declined with a reason (optionally mailed too). Project settings gain the
switch that enables the form and the shareable link to it, which previously
could only be turned on by writing to the API directly.

## A cycle can end

Clicking a cycle opens its details: live done-vs-total progress, and a
burndown chart drawn from the daily snapshots the worker has been collecting
since cycles shipped, with an ideal line to the end date. Completing the cycle
rolls open tasks to the backlog or into the next cycle. Cycles auto-activated
on their start date but had no way to finish; a sprint that ended stayed
active forever.

## Moving a task moves the work

Move a task to another project and the whole subtree goes with it, children
re-parented to the new ids. Comments, relations, external links, git links,
attachments, logged time and a running timer all re-point to the new tasks in
place, keeping authors, timestamps and invoice links exactly as they were.
Before this, comments stayed on the soft-deleted original and subtasks were
orphaned under a parent nothing could open. Project-scoped fields reset
honestly: status becomes the target's default, and type, cycle and milestone
clear, since each belongs to the source project.

## Templates and recurring rules have a face

Project settings gain two sections: task templates (name, task title,
priority) and recurring rules that instantiate a template daily, weekly or
monthly, with an active toggle and the next run date. The scheduler that
creates the tasks has been running all along; it finally has a UI feeding it.

## Milestones hold tasks

From the parallel line of work on master: a task can carry one of its own
project's milestones, the tasks view groups and filters by milestone, and the
overview's milestone list shows real done-vs-total counts computed from the
tasks rather than a hand-ticked checkbox. Projects also keep files now, gated
by project membership, and the task list pages through the whole project
instead of silently showing its newest 50.

## Smaller true things

- Task lists and boards mark tasks blocked by an open "blocks" relation. The
  relation existed; no view surfaced it.
- The projects list reads its completion rings from one grouped query
  (`GET /projects/task-counts`) instead of pulling every task of every
  project, one project per row.
- Tied task orderings resolve by the tasks' own sequence, not by whatever
  order the API returned.

## Upgrading

Nothing is removed and nothing changes shape incompatibly.

- One additive migration (`tasks.milestone_id`).
- New endpoints: `POST /leads/bulk`, `POST /import/leads`,
  `GET /export/leads.csv`, `GET /sales-analytics`,
  `GET /projects/task-counts`.
- `GET /leads` now returns `{ data, truncated }`; the `data` field is
  unchanged, so existing consumers keep working.
- `GET /tasks` rows carry a new `blocked` boolean.
