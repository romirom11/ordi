# ordi v1.12.0

CRM record pages stopped being their own little app. The client and deal
cards now have the same shape as the project and task records they sit
next to, and a project can finally show the leads sold into it.

## One shape for every record

The client card had drifted: a centred grid of its own width, bordered
property cards with hand-rolled inline inputs, a header carrying both the
record's identity and a toolbar, and empty sections that each burned a
third of a screen. The deal card had drifted the same way. Both now follow
the project and task pages:

- the header is one line - breadcrumb, avatar or icon, editable name, and
  nothing else. The status pill, domain link, stage dropdown, owner and
  project pickers, and the add-note / new-deal / overflow buttons are gone,
  because each either duplicated a section's own action or repeated what
  the properties rail already shows;
- content runs at full width, with the properties rail pinned to the right
  edge. Below 1100px the rail stacks above the content instead of hiding,
  since status, stage and owner live only there now;
- the rail carries every field as a labelled row with hover chips: for a
  client, status, owner, domain, billing email, currency, terms, created,
  projects and files; for a deal, stage, client, project, owner, amount,
  currency, close date, lost reason, created, custom fields and files;
- empty sections collapse to a single line instead of a full-height empty
  state. A fresh client used to read as three screens of nothing.

Files moved into the rail on both cards, as a compact list with upload on
the heading and delete on row hover.

## Activity on the client

The client card gets an activity trail - who changed what and when, read as
sentences. The audit API was already generic, so the project's feed became
a shared component rather than a second implementation, and the deal page
dropped its own copy of the same rendering.

## A project shows its leads

A deal could always point at a project, and the pipeline could always
filter its board by one. The other direction was missing: the project could
not show its own pipeline. That is the view a product project needs - a
delivery project collects one client's deals, but a SaaS project collects
leads from many different companies at once.

The project overview now lists them, with the open pipeline total beside
the count. Two permissions gate it independently: `deals.read` decides
whether the section exists at all, and `crm.read` decides whether a row may
name the client it came from. Neither rides on being able to open the
project, because project membership alone gets a guest onto a shared
product project, and a guest must never see other clients' deals.

## Also in this release

- Task and project labels are two vocabularies instead of one flat pool.
  The project rail no longer offers "Bug", the write paths reject a label
  from the wrong side with a 400 rather than dropping it silently, and one
  picker with search and inline creation replaced the two that existed.
  Migration 0013 splits shared labels, keeping the original id with the
  tasks so filters and history keep resolving.
- Repository bindings store the repository, not GitHub's own id. Linked
  repos used to render as bare numbers, and - the quiet half - webhook
  delivery could not resolve them, so branches and pull requests never
  linked to tasks on repos connected that way. Migration 0012 repoints the
  bindings written by the old code.
- The GitHub App and OAuth callbacks stopped doubling `/api`. Creating the
  app from the manifest redirected to `/api/api/v1/...` and 404'd, so the
  one-time conversion code was never exchanged and ordi ended up with none
  of the app's credentials. `API_URL` is now normalised on read, so either
  spelling of the variable produces the same callback URLs.
- A project's client and type edits actually persist. `PATCH /projects/:id`
  silently dropped both keys, so the rail's pickers and CRM's "link
  existing project" returned 200 while writing nothing.
