# ordi v1.6.0

One container is now the whole application. The API serves the built web app
itself; nginx is gone from the deployment story, and with it the entire class
of "this path never reached the API" bugs – including the one that kept MCP
clients from connecting to real instances.

## Why

The web app used to ship as a separate nginx container that proxied `/api/`,
`/healthz` and `/.well-known/` to the API. That boundary was pure liability:

- its config hardcoded the upstream `api:3000`, a name that only resolves in
  our own compose network – so on Dokploy/Coolify (which rename services)
  the shipped config **could not** work, and every such deployment replaced
  it with a hand-written mount, frozen on the day it was written;
- a frozen config silently missed every route added later. `/.well-known/`
  (v1.5.0) never reached those instances, and the visible symptom was Claude
  failing with *"Couldn't register with ordi's sign-in service"* while the
  site worked perfectly;
- every hop in front had to re-learn scheme and host forwarding.

Serving the frontend from the application process is how self-hosted products
do this (n8n, Directus, Outline, Grafana, Gitea). Now the server that owns
`/api` also owns `/`, `/assets` and `/.well-known` – there is nothing left to
misroute.

## What the single container does

- Serves the SPA: `index.html` with `no-cache`, hashed `/assets/*` with
  `immutable` for a year, gzip precompressed at build time and served via
  `Accept-Encoding` (no per-request compression cost).
- Answers every SPA route with the app shell, but never swallows API paths:
  an unknown `/api/v1/*` stays a JSON answer, exactly as before.
- Serves OAuth discovery on the same port, so MCP connectors work with zero
  routing configuration.
- SSE streams directly, with no proxy buffering to configure.

Covered by tests (SPA fallback, cache headers, precompression, API-shape
preservation) and by CI, which boots the image and asserts all of the above
plus discovery under forwarded headers.

## APP_URL decides the scheme for its own host

`X-Forwarded-Proto` describes the nearest hop, and a common self-hosted chain
reports the wrong thing: a Cloudflare tunnel terminates TLS, then reaches a
router over plain http, and the router overwrites the header with its own
entrypoint's scheme. The API then advertised `http://` URLs for an https
site, and MCP clients refused the connector.

If `APP_URL` names the request's host, its scheme now wins – the operator who
wrote `APP_URL=https://this.host` has stated what the site is. Other hosts
still follow the forwarded headers, so multi-domain setups are unaffected.

## Settings → MCP diagnoses discovery

Settings → MCP fetches the OAuth discovery document from the instance's own
root and names the problem when there is one: a proxy answering
`/.well-known/` with the web app, a scheme or host mismatch, or an
unreachable document – each with its fix. Useful for anyone who fronts ordi
with their own proxy.

## Upgrading

No schema changes.

- **Dokploy / Coolify / any router:** point the domain at the **`api`**
  service, **port 3000**, path `/`. Delete the `web` service and any nginx
  config mount you added for it. No new env vars.
- **docker-compose:** pull; `web` is gone from both compose files, `api` now
  also answers on the old web port mapping.
- The desktop app and MCP connectors need no changes; they talk to the same
  public URL as before.
- The nginx web image still builds and works this release (deprecated, now
  with the upstream configurable via `API_UPSTREAM`) for deployments that pin
  it; it will be removed later.
