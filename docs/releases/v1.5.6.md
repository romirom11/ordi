# ordi v1.5.6

Adding ordi as an MCP connector in Claude failed with *"Couldn't register with
ordi's sign-in service"*. The reason was in our own discovery documents.

## What was wrong

Every URL in them – `issuer`, `authorization_endpoint`, `token_endpoint`,
`registration_endpoint` – was built from `APP_URL`. That works only if
`APP_URL` happens to equal the address the client used. When it does not (it
defaults to `http://localhost:5173`, and `docker-compose.yml` ships
`http://localhost:8080`), the failure is confusing rather than obvious:
discovery *answers*, because the client reached the real host on its own, and
then hands back a registration endpoint on localhost that the client's servers
cannot reach. RFC 8414 also requires `issuer` to match where the metadata was
fetched from, so a mismatch is invalid regardless of reachability.

The bundled nginx had the same bug from the other side: the `/.well-known/`
block proxied to the API without passing `Host` at all, so the API saw
`api:3000` and would have advertised that. Nothing passed
`X-Forwarded-Proto` either, so behind a TLS terminator we would have said
`http://` on an https site.

## What changed

Discovery reports the origin the request actually arrived on –
`X-Forwarded-Host`, then `Host`, with `APP_URL` only as a fallback. nginx
forwards `Host`, `X-Forwarded-Host` and `X-Forwarded-Proto`, honouring an
outer proxy's `X-Forwarded-Proto` since TLS is normally terminated above the
container.

Two tests pin it: discovery served to `Host: ordi.example.com` must name that
host in every endpoint and in the `WWW-Authenticate` header on `/mcp`, and
registration must accept the exact body Claude sends. CI additionally boots
the web image and checks discovery through nginx, which also catches a broken
nginx config.

## Checking your own proxy

```
curl -s https://ordi.example.com/.well-known/oauth-authorization-server
```

`issuer` and `registration_endpoint` must be on your public domain, not
`localhost` and not `api:3000`.

Two things worth knowing regardless of this fix: registration is performed by
the client's servers, not by your browser, so the instance has to be reachable
from the internet over https – a LAN-only instance still needs a hand-made
token. And `APP_URL` remains the source of links in emails and PDFs, so keep
it correct.

## Upgrading

No schema changes. Server-side only: redeploy the API and web images. The
desktop app is unaffected but is rebuilt for version parity.
