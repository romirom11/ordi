# ordi v1.19.0

Attachments have been in ordi since v1.17.0, and on a laptop they worked. On a
server they did not. The browser was handed a presigned URL to
`http://minio:9000` – a hostname that exists only inside the docker network –
so every upload from the UI failed, and behind https it failed twice over as
mixed content. The deployment docs said "keep the bundled MinIO" while the prod
compose had no MinIO in it at all.

This release is about closing that gap: files now travel through the API, the
prod stack brings its own storage, and in-stack addresses stop trusting names
another project on the same PaaS network might also be using. The CRM gets the
small readability work that was left over from v1.18.0.

## Files travel through the API

All file bytes now go through the API, which talks to the bucket over the
internal network. No presigned URL ever reaches the browser, so there is no
second public vhost to stand up, no CORS to configure, and MinIO's S3 port is
no longer published to the host.

- `POST /attachments` takes the file itself as multipart, plus the optional
  entity it belongs to. It validates extension, size and permissions, generates
  the storage key server-side and puts the object. It replaces
  `/attachments/presign` and `/attachments/register`.
- `GET /files/:id/:token` streams the object with its stored content type, a
  unicode-safe `Content-Disposition` and immutable caching, instead of
  redirecting to storage. `/attachments/:id/url` returns that same signed path.
- The 25MB cap is what makes proxying cheap, and one flow now serves bundled
  MinIO and external S3/R2 identically.

Because the storage key is chosen server-side and never by the caller, the
register-a-foreign-key hole that v1.17.0's `keyToken` defended against is gone,
and the defence went with it. Tests exercise the full round trip against an
in-memory storage mock, including streaming the bytes back anonymously through
the signed link.

## Preview in place, and refusals that name the cause

Clicking a file's name opens a preview built entirely on what a browser renders
natively: images, the built-in PDF viewer, video, audio, and text-ish files
(code, CSV, JSON, logs) as monospaced text with a 1MB cap. Anything else says
plainly that the type has no preview and offers the download; the download icon
still downloads directly.

Serving files from the app's own origin makes an uploaded HTML or SVG a
stored-XSS vector the moment it is opened as a page, so `/files` answers
scriptable types (html, svg, xml) with `Content-Security-Policy: sandbox` – a
unique origin and no scripts. Embedding as `<img>` is unaffected; image
contexts never ran scripts to begin with.

Picking files takes several at once now: they upload sequentially, with one
summary toast and the first failure named per file. And a storage refusal used
to surface as an unhandled 500 with the real reason visible only in the API
logs, which reported an operator's misconfiguration as a server crash.
`InvalidAccessKeyId`, `SignatureDoesNotMatch`, `NoSuchBucket` and `AccessDenied`
now map to a 422 that names the environment variable to check, and a missing
object to a 404.

## The prod stack brings its own MinIO

`COMPOSE_PROFILES=minio` brings up object storage inside the prod stack, so a
self-hosted install no longer has to hand-roll it. Root credentials are the
same `S3_ACCESS_KEY`/`S3_SECRET_KEY` pair the api uses – one source, nothing to
drift – a one-shot `minio-init` creates the bucket on first boot, and nothing is
published to the host.

The profile's environment variables stay optional-with-default on purpose:
compose interpolates even profile-disabled services, so a required-var guard
there would break every deployment that uses external S3.

## Names that cannot collide

On a PaaS the router attaches `api` to a shared network (Dokploy, Coolify), and
a container on two networks resolves names against both. A generic `db` or
`minio` can therefore land on another project's container that happens to carry
the same service name. That is not hypothetical: it produced an
`InvalidAccessKeyId` from a foreign MinIO and an auth failure from a foreign
Postgres on a real deployment, both indistinguishable from bad credentials.

The prod stack's services now carry unique aliases – `ordi-db`, `ordi-minio` –
that exist only on the stack's own private network, and every in-stack address
uses them: `DATABASE_URL`, the bundled-MinIO docs and `minio-init`.

## The lead table reads at a glance

Lead rows answer a right-click like every other list in the app: open in a new
tab, copy link, open the company, a status submenu (nurture excluded – it needs
a return date a menu cannot ask for), an owner submenu, and delete behind the
usual confirm. A converted lead offers navigation only, matching its frozen
detail page.

And lead statuses have colour. All nine of them rendered in the same grey,
because the status map only ever held the four company statuses and every lead
fell through to the fallback: Disqualified looked exactly like Ready to
contact. Leads are now toned by whose move it is rather than by funnel depth –
indigo for the ones we owe an action, amber for the one asking a human to
decide, green while the conversation is live or won, red for disqualified, grey
for everything waiting on someone else or already finished. Terminal and parked
rows recede so the actionable ones carry the colour; a table where every row is
coloured is the grey table again.

## Upgrading

No database migration. Two things to check on a self-hosted install:

- **In-stack addresses.** Point `DATABASE_URL` at `ordi-db` and, if you run the
  bundled storage, `S3_ENDPOINT` at `http://ordi-minio:9000`. The old service
  names still resolve inside the stack, so nothing breaks on upgrade, but they
  are the names that can collide on a shared PaaS network.
- **The prod compose no longer publishes MinIO's S3 port.** If something
  outside the stack was reaching the bucket through that published port, it
  needs its own route now. The app itself does not: all file traffic goes
  through the API.

If you call the API directly, `POST /attachments/presign` and
`POST /attachments/register` are gone. Send the file to `POST /attachments` as
multipart instead; it returns the same attachment record. The browser clients
in this repo were updated with the change.
