# ordi v1.6.1

Observability for the MCP connection path, born from a live "Authorization
failed" that neither side could see into.

## OAuth failures are loud now

The consent screen opens, you click Authorize - and the last step happens
between machines: the MCP client's backend exchanges the one-time code for a
token at `/api/v1/oauth/token`. Until now every rejection on that path was a
silent 400: no log line, nothing for the operator to look at, only an opaque
"authorization failed" in the client.

Every step now logs its outcome: client registrations (name and redirect
hosts), issued tokens (client and user), and every rejection with the exact
failing check - unknown client, unregistered redirect_uri, expired or reused
code, wrong client for the code, redirect_uri mismatch, PKCE failure,
malformed exchange body. If connecting a client fails, the API log names the
step and the reason; if nothing appears in the log at all, the request never
reached ordi and the problem is in front (proxy, WAF, tunnel).

## The state parameter cap was ours, not the spec's

`state` is the client's opaque blob, echoed back verbatim. We capped it at
512 characters; clients whose state is a signed payload can exceed that, and
the rejection was - see above - silent. The cap is 4096 now.

## CI gates releases on the whole flow

The docker job seeds an owner in the booted image and performs the exact
sequence an MCP client does: dynamic registration with the byte-for-byte
body Claude sends, approve as the signed-in user, PKCE code exchange over
form encoding, then `initialize` and `tools/list` over Streamable HTTP,
requiring a full tool catalog back. A release cannot ship if connecting a
client is broken anywhere along that path.

## Upgrading

No schema changes, server-side only: redeploy the API image. If an MCP
connector fails after this release, the API log now tells you which step and
why - and an empty log at the failure time means the request was blocked
before reaching ordi.
