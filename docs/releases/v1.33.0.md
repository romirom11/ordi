# ordi v1.33.0

The agent worker can run without the database, so the container that
executes model-authored code holds nothing of the API's; a run survives its
own log and pushes to a branch that moved; and a finished run leaves one
closing comment, in the thread's language, addressed to a person.

## The agent worker, without the database

An agent run is the one place in ordi where code the model wrote is
executed: the repository is cloned, commands run in it, a branch is pushed.
Until now the process doing that lived in the `api` container with
`DATABASE_URL`, `ENCRYPTION_KEY`, `AUTH_SECRET`, the S3 and SMTP credentials
and every other secret in reach, and the documented production split moved
it to a second container with the same environment – which moved the blast
radius without shrinking it.

- **One interface between the worker and the platform.** Everything the
  worker needs that lives in a row or behind a secret – the claim, the
  decrypted credential chain, the repository token, the run token and the
  brief, the event log, a fresh token for the push, and what a finished run
  means for the task (the comment, the status move, the follow-up) – is now
  `domains/agents/run-service.ts` on the API side, reached through
  `RunBackend`. The worker itself is git, the filesystem and the runtime
  adapter, and imports nothing that opens the database.
- **Two ways to reach it.** Inside the API process the worker calls the
  service directly, so `docker compose up` is unchanged and the existing
  tests run through that path unmodified. As a process of its own
  (`pnpm --filter @ordi/api exec tsx src/agent-worker.ts`) it talks to
  `/api/v1/agent-worker/*` with one shared secret – `AGENT_WORKER_SECRET`,
  set on both services; without it the router answers 503 and a worker
  outside the API is simply not a thing the install does.
- **What the worker holds.** The model credential, the repository token and
  its own run token, for the run in front of it – each scoped, the run token
  revoked when the run ends. It needs `ORDI_API_URL`, `AGENT_WORKER_SECRET`,
  `AGENT_WORKER_CONCURRENCY` and `AGENT_WORK_DIR`, and warns in its log if a
  PaaS hands it the API's variables anyway. Secret scrubbing stays where the
  log is written, so a remote worker's events are as clean as a local one's.
- **The compose file carries the service.** `docker-compose.prod.yml` has
  the `agent-worker` service ready to uncomment; the checkout volume moves
  to it, and `api` sets `AGENT_WORKER_ENABLED=0` so it stops claiming runs
  itself. Runs are claimed with `SKIP LOCKED` on the API side, so nothing is
  executed twice even with the flag wrong for a moment. `docs/deployment.md`
  §3b has the steps; `docs/architecture-decisions.md` §12 the reasoning.

## A run survives its own log, and pushes to a branch that moved

- A tool result carrying a NUL byte – a binary read, a build log – made
  Postgres refuse the run event, and that one failed write ended the agent's
  session mid-task. NUL bytes are stripped from every event payload, and a
  failed event write is a warning in the worker log rather than the end of
  the run.
- The push after a run assumed the branch on origin had not moved. The
  previous run's WIP push, a teammate's commit or a commit the agent amended
  made it non-fast-forward, and the run failed with the work stranded on the
  worker. The branch is fetched first and the local commits replayed on top
  of origin's tip – a conflicting hunk goes to the local side; a
  modify/delete the merge cannot settle is undone and reported, never
  forced. The agent is told that commits already on the branch are pushed
  and not to rewrite them; `git commit --amend`, `git rebase`, `git reset`
  and `git branch -f` join the blocked commands.

## One closing comment, in the thread's language, addressed to a person

A finished run left two comments on the task: the agent's own reply to the
teammate, in their language, and then the platform's copy of the report
summary in English saying the same thing again.

- The platform posts the summary only when the agent left no comment during
  the run; the agent's closing comment is the report for the people on the
  task, and the pull request carries the summary either way.
- The brief asks for one closing comment – what changed and why, what is
  needed from a person – with mid-run comments reserved for a blocker or a
  change of approach, in the language of the task and the people in the
  thread. `verification` and `risks` stay English for the pull request.
- The brief names the person to answer – the follow-up's author, or whoever
  assigned or retried – with their user id, and `comment_on_task` takes
  `mentionUserIds`: `@Name` in the text becomes a real mention (the chip in
  the editor, the notification on the server), and a mentioned person the
  text does not name is put at the start. The platform's own comments
  (summary fallback, needs input, stopped, failed) mention that person too.
  `textToDoc` in `@ordi/shared` grew the `mentions` option that does this.

## Upgrading

No migration. Pull the image and restart:

```
docker compose pull && docker compose up -d
```

`latest` moves you to this release; `ORDI_VERSION=1.33.0` pins it. The desktop
app updates itself from the release.

Nothing changes unless you opt in. To run agents in a container of their
own, set `AGENT_WORKER_SECRET` on `api` and on the new `agent-worker`
service, set `AGENT_WORKER_ENABLED=0` on `api`, and move the `agent_work`
volume to the worker – `docs/deployment.md` §3b walks through it.
