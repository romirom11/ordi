# ordi v1.5.5

The sidebar has one identity row instead of two, the macOS window buttons get
a strip of their own, and nothing tells you your own name any more.

## One row at the top, none at the bottom

The sidebar used to open with the workspace name and close with a row showing
your avatar and your name. The second one was pure noise: you know who you
are. What you occasionally need is *what account am I signed in as*, and that
is a question for the moment you open the menu, not for every second of the
day.

So the two rows are one row at the top, and it holds everything:

```
[A] Acme Agency ⌄          🔍  ✎
```

The dropdown carries the email as its heading, then Profile, Invite user,
Download the desktop app (browser only), the theme choice, and Sign out.
Search and new-task moved into the same row as icons, which frees the row
they used to own – the new-task button keeps its `C` shortcut and gains a
tooltip in place of its label.

The workspace name gets 91px before it ellipses, which fits `Acme Agency`
exactly; longer names truncate rather than escaping the sidebar.

## The workspace name moved below the macOS window buttons

v1.5.4 put the name *beside* the traffic lights by indenting it 84px. That
kept one tidy row, but the name then started a third of the way into a 224px
sidebar, and the indent only ever made sense on macOS.

The sidebar now opens with a short empty strip that belongs to the window
buttons – `trafficLightPosition` centres them inside it – and the identity
row starts below, flush with the left edge on every platform. The strip is a
drag region, so the corner still moves the window. Tabs are unaffected: they
live in the right-hand column and still share the row with the buttons.

On Windows, Linux and in the browser there is no strip at all.

## Notifications is a row with a count

The bell was an icon with a badge on its corner. At two digits the badge
covered most of the glyph – a real problem at 13 unread, never mind 40. It is
a navigation row at the top of the nav now, with the count right-aligned, so
it reads at a glance and has room for three digits.

## Settings is a row too

It was an item inside the workspace dropdown. It is a destination, so it
reads as one: a row at the foot of the nav with a gear icon and an active
state, one click instead of two. Shown only to users who can manage settings,
users or roles.

Inviting users left the sidebar's own menu structure and lives in the
workspace menu (and in Settings → Users, which is where it always was).

## MCP connectors could not register

Adding `https://<instance>/api/v1/mcp` as a connector in Claude failed with
*"Couldn't register with ordi's sign-in service"*, and the reason was in our
own discovery documents.

Every URL in them – `issuer`, `authorization_endpoint`, `token_endpoint`,
`registration_endpoint` – was built from `APP_URL`. That works only if
`APP_URL` happens to equal the address the client used. When it does not (it
defaults to `http://localhost:5173`, and `docker-compose.yml` ships
`http://localhost:8080`), the failure is confusing rather than obvious:
discovery *answers*, because the client reached the real host on its own, and
then hands back a registration endpoint on localhost that the client's server
cannot reach. RFC 8414 also requires `issuer` to match where the metadata was
fetched from, so a mismatch is invalid regardless of reachability.

Discovery now reports the origin the request actually arrived on – forwarded
headers first, then `Host`, with `APP_URL` only as a fallback.

The bundled nginx had the same bug from the other side: the `/.well-known/`
block proxied to the API without passing `Host` at all, so the API saw
`api:3000` and would have advertised that. It now forwards `Host`,
`X-Forwarded-Host` and `X-Forwarded-Proto` (honouring an outer proxy's
`X-Forwarded-Proto`, since TLS is normally terminated above this container),
and CI boots the web image and asserts that discovery through nginx names the
public host.

If you run your own proxy in front of ordi, check it with:

```
curl -s https://ordi.example.com/.well-known/oauth-authorization-server
```

`issuer` and `registration_endpoint` must be on your public domain. Note also
that registration is performed by the client's servers, not your browser, so
the instance has to be reachable from the internet over https – a LAN-only
instance still needs a hand-made token.

## Upgrading

No schema changes. The macOS window-button placement lands with the app build;
the sidebar changes apply everywhere, including self-hosted web. The MCP fix
is server-side: redeploy the API and web images.
