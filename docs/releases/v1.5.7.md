# ordi v1.5.7

v1.5.6 fixed OAuth discovery when `APP_URL` was stale. Investigating a live
instance where connecting Claude still failed exposed the actual root causes –
both ours, not the deployment's – and this release removes them.

## The web image is now deployable outside our compose file

The nginx config inside the web image hardcoded its API upstream as
`http://api:3000`. The name `api` only resolves inside our own compose
network, so on any PaaS that names services differently (Dokploy, Coolify),
the config could not work as shipped – and every such deployment was forced
to replace it with a hand-written file mount.

That is worse than an inconvenience: a replaced config is frozen on the day
it was written. We added the `/.well-known/` route in v1.5.0 and the
forwarded headers in v1.5.6 – a config written before that never received
either, and the visible symptom is an MCP client failing with *"Couldn't
register with the sign-in service"* while the site itself works perfectly.

The config is now a template rendered on every container start by the stock
nginx image mechanism, with the upstream as an env var:

- **`API_UPSTREAM`** (default `api:3000`) – set it to wherever your API
  service lives, e.g. `API_UPSTREAM=ordi-api:3000` on Dokploy.

If your deployment has a file mount over `/etc/nginx/conf.d/default.conf`,
remove it and set the variable instead – from then on routing fixes arrive
with releases. CI now boots the web image against an API container that is
deliberately *not* named `api`, so the override path itself is tested.

## APP_URL decides the scheme for its own host

`X-Forwarded-Proto` is set by the *nearest* proxy, and a common self-hosted
chain reports the wrong value: a Cloudflare tunnel terminates TLS, then
reaches a router over plain http, and the router overwrites the header with
its own entrypoint's scheme. The API then advertises `http://` URLs for a
site that is https everywhere the user can see, and MCP clients refuse the
connector.

An operator who wrote `APP_URL=https://this.host` has stated what the site
is; a hop header contradicting that for the same host describes the last hop,
not the client. So `APP_URL` now wins – for the scheme only, and only when
its host matches the request. Any other domain still follows the forwarded
headers, so multi-domain setups are unaffected.

## Settings → MCP diagnoses discovery

MCP clients read the OAuth discovery document from the **root** of the domain
before anything else; the path is fixed by RFC 8414/9728 and chosen by the
client. When the deployment answers it with the SPA's `index.html`, the only
symptom used to be an opaque error inside the client.

Settings → MCP now fetches that document itself and names the problem: the
proxy answering `/.well-known/` with the web app, a scheme or host that does
not match this address, or a document that cannot be reached – each with its
fix.

## docker-compose.prod.yml

A production compose for PaaS or plain docker-compose-behind-a-router
deployments: no published ports, everything from env vars, required values
enforced (`APP_URL`, `AUTH_SECRET`, `ENCRYPTION_KEY`, `POSTGRES_PASSWORD`).
Point the router at the `web` service, port 80, path `/` – nothing else.

## Upgrading

No schema changes. Server-side only: redeploy the API and web images. If you
replaced the web service's nginx config, delete that mount and set
`API_UPSTREAM` instead.
