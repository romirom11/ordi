# ordi v1.5.7

v1.5.6 fixed OAuth discovery for instances whose `APP_URL` was stale. This
release fixes the other half of the same story – deployments where the proxy
chain itself reports the wrong thing – and makes the failure visible inside
ordi instead of only inside the MCP client.

## APP_URL decides the scheme for its own host

`X-Forwarded-Proto` is set by the *nearest* proxy, and a common self-hosted
chain reports the wrong value: a Cloudflare tunnel terminates TLS, then
reaches a router (Traefik, and friends) over plain http, and that router
overwrites the header with its own entrypoint's scheme. The API then
advertises `http://` URLs for a site that is https everywhere the user can
see, and every MCP client refuses the connector.

An operator who wrote `APP_URL=https://this.host` has stated what the site
is. A hop header contradicting that for the same host describes the last hop,
not the client. So `APP_URL` now wins – for the scheme only, and only when its
host matches the request. The host still comes from the request, so serving
several domains is unaffected, and any other domain still follows the headers.

## Settings → MCP says what is wrong

MCP clients read the OAuth discovery document from the **root** of the domain
before anything else – the path is fixed by RFC 8414/9728 and chosen by the
client, not by us. A deployment that routes only `/api/` to the API answers it
with the SPA's `index.html`, and the client then reports something opaque
("couldn't register with the sign-in service") with nothing pointing at a
missing proxy route.

Settings → MCP now fetches that document itself and names the problem: the
proxy answering `/.well-known/` with the web app, a scheme or host that does
not match this address, or a document that cannot be reached at all – each
with the fix.

## docker-compose.prod.yml

The nginx config that routes `/.well-known/` to the API ships in the web
image, but a PaaS deployment that hand-writes its own config for that service
silently loses it – and hand-written configs are what happens when the repo
offers only a compose file full of `localhost` and published ports.

So there is now a production compose meant for Dokploy, Coolify or plain
docker compose behind a router: no published ports, everything from env vars,
required values enforced (`APP_URL`, `AUTH_SECRET`, `ENCRYPTION_KEY`,
`POSTGRES_PASSWORD`). Point the router at the `web` service on port 80 with
path `/` and add no other routing rule – nginx inside the image handles
`/api/`, `/healthz`, `/readyz` and `/.well-known/`.

`docs/deployment.md` says this explicitly, including why replacing that config
breaks MCP connectors while leaving the site perfectly functional.

## Upgrading

No schema changes. Server-side only: redeploy the API and web images. If you
run a custom nginx or router config, make sure `/.well-known/` reaches the API
– without it MCP clients cannot connect, whatever else is configured.
