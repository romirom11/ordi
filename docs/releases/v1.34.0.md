# ordi v1.34.0

Agent runs execute in their own container out of the box, and a run that
stops to ask a question keeps the work it had done.

## Agent runs in their own container, by default

v1.33.0 made the agent worker able to run without the database: as a process
of its own it talks to the API over `/api/v1/agent-worker/*` with one shared
secret and holds only what the run in front of it needs. But the compose
files still ran it inside the `api` container, and the separate service was
a commented-out block for whoever went looking. So a fresh install executed
model-authored code next to `DATABASE_URL`, `ENCRYPTION_KEY` and
`AUTH_SECRET`, and the split that the docs recommended for production was
not what production got.

- **Both compose files run the `agent-worker` service.** Same image, the
  worker command, an environment of four variables, and the `agent_work`
  volume for checkouts and session transcripts – on the worker only, the
  `api` needs none. `api` sets `AGENT_WORKER_ENABLED=0` so it never claims
  a run itself.
- **`AGENT_WORKER_SECRET` is required by `docker-compose.prod.yml`**, the
  way `AUTH_SECRET` is: any random string (`openssl rand -hex 32`), set once
  and read by both services. The quick-start `docker-compose.yml` ships a
  placeholder, so `docker compose up` still works with nothing configured.
- **The worker waits for the api.** `api` gets a healthcheck on `/healthz`
  and the worker depends on it, so a slow first migration delays the worker
  instead of filling its log with "API unreachable". Docker does not restart
  an unhealthy container, so the check can never take the api down.
- **`ordi-api` on the compose network.** The worker reaches the api by that
  alias for the reason the database is `ordi-db`: on a shared PaaS network a
  generic `api` can resolve to another project's container.
- **`docker-compose.build.yml`** points the worker at the locally built
  image too, so a fork or a branch check runs both containers from one
  build.
- **Settings → Agents** warns about a missing worker only when no worker at
  all is online. It used to warn whenever the API's own worker was off,
  which is now the normal shape of a deployment.

Nothing changes in how a run executes: claiming, the brief, the event log,
the per-run token and the push all stayed where v1.33.0 put them.

## A question from the agent keeps its work

A run that ended with `needs_input` – the agent stopping to ask the task's
author something – pushed nothing. The checkout, with whatever the agent had
committed before asking, was deleted when the run ended, and the follow-up
after the reply resumed a session that remembered files no longer on disk,
found no branch on origin and named a new one.

`needs_input` now takes the same path as a run stopped by a limit, a timeout
or a cancel: the work so far goes out as a `WIP` commit on the task's
branch, no pull request is opened, and the follow-up continues on that
branch in the same session. The dispatch test for `needs_input` asserts the
push and that no pull request url was recorded.

## Also

- `CLAUDE.md` at the repository root states the branch naming rule
  (`feature/`, `fix/`, `docs/`, `release/`), so an agent working in the
  repository names its branches like everyone else.

## Upgrading

Server: `docker-compose.prod.yml` now refuses to start without
`AGENT_WORKER_SECRET`, so add it to the environment before `docker compose
pull && up -d` (on Dokploy: Environment, then Redeploy). If you had
uncommented the `agent-worker` block yourself, delete your copy – the
service is in the file; if `api` had `AGENT_WORKER_ENABLED=1` in its
environment, remove it so the api does not claim runs next to the worker.
The `agent_work` volume is the same one, so session transcripts and
follow-ups carry over. No migrations. `docs/deployment.md` §3b has the
full section.

The desktop app is unchanged apart from its version number.
