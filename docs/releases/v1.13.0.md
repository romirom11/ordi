# ordi v1.13.0

A role with "view projects" listed a project and then answered "Project not
found" to everything done inside it. Pulling on that thread found the same
mistake in the knowledge base, in four places that read project-owned rows
straight out of the database, and in the leave form, which nobody could
submit at all.

## Workspace projects and spaces answer to the role

`workspace` visibility granted the viewer level and nothing else, so the
write permissions only ever applied to resources a user had been added to
individually. A role holding `kb.read` and `kb.write` could not create a
page anywhere, because creating one asks for space *editor* and the only
way to hold that was a `space_members` row. A role holding `projects.write`
could not touch a project it was not a member of. Both failed as "not
found" - the same message the API uses for something that does not exist -
on a resource the app had just put on screen.

Workspace visibility is the "unrestricted" resource of the authorization
rule, and that applies to the whole rule rather than to reads alone. The
level now comes from the role: `projects.read` views a workspace project,
`projects.write` works and administers it, `kb.read` views a workspace
space, `kb.write` edits it. Private resources stay membership-only.

Two things follow. The domain read permission stays the floor, which keeps
the listing and the detail in agreement - workspace listing is keyed off
`projects.read`, so nothing can answer that is listed nowhere. And a level
the actor lacks on a resource it *can* see is now a 403 naming what is
missing, with 404 kept for resources outside visibility, where hiding
existence is the point.

The project page asks the same resolver the API authorizes with instead of
reading `projects.write` directly. That check hid the settings from project
admins who hold no global write, and offered edits to viewers that the
server then refused.

## Resource access reaches the feeds, the board and search

Membership decided who could open a project, and then four places read its
rows with only a permission check in front of them:

- the home feed filtered activity by entity type ("may this role see task
  activity") and never by which task, so a private project's names, task
  titles and milestones scrolled past on the dashboard of anyone holding
  `projects.read`;
- its own "my tasks" listed assignments in projects the user could not
  open, each one a click to a 404;
- `/audit/entity/:type/:id` had no check at all - any authenticated user
  could read the trail of any id they could name, including an employee's
  or an invoice's. It now takes the same permission the home feed applies
  per entity type, then the resource check;
- Resourcing listed allocations for every project, and search matched KB
  pages in spaces the actor cannot open.

Underneath: `accessibleSpaceIds`, the space counterpart of
`accessibleProjectIds`, and a resolver that maps a batch of activity
records back to the project or space that owns them - tasks, comments,
cycles, pages and page comments through their parents. A record that no
longer resolves is dropped rather than shown. Full audit access
(`audit.read`) is exempt from all of it, since seeing everything is its
purpose.

## Requesting leave works

The leave form never sent an `employeeId`, and the API required one, so
every submission failed as "employeeId: Required" - for everybody, not just
for restricted roles. The field is optional now and means "whoever is
asking", with a plain message when an account has no employee card behind
it. Leave writes authorize per request (own, manager, approver - as the
service already did) instead of demanding `people.read`, which neither the
Member nor the Manager role carries; a requester without it reads their own
leave and nobody else's.

The list rendered "–" for the person and the type on every row, because the
query returned raw request rows while the UI reads the two names, so a queue
of pending requests said nothing about who was asking for what. The form
also swallowed the API's message behind a generic failure toast, and gained
a "For" picker for the roles that may file on someone else's behalf.

## Leave types are configurable

Settings → Leave types: the absence vocabulary the request form offers, and
what each type does - paid, needs an approval, draws down a balance and the
annual quota it draws from, half days, carry-forward with its limit and
expiry. The API had the full CRUD behind `people.manage_leave` since the
module landed; nothing in the app reached it, so the three seeded types
were all anyone could ever request.

## An agent can read back what it wrote

Reported from an agent run against a live workspace, through MCP:

- **Read back a write.** `list_companies` / `list_contacts` / `list_deals`
  dropped `customFields` on the way out and there was no single-record read
  at all, so the only way to see a deal's fields was `move_deal` - changing
  a record in order to look at it. Every list carries them now, and
  `get_company` / `get_contact` / `get_deal` read one record whole.
- **Change one field.** There was no update for any CRM entity, so records
  created before a field existed stayed empty forever. `update_company`,
  `update_contact` and `update_deal` fill that in, and `customFields` merge
  by key server-side for every entity that has them. Assigning the blob
  wholesale meant a caller who set one field erased the rest of that
  record's custom data - invisible in the UI, which round-trips the whole
  object, and destructive for everything else.
- **Read notes, and fix them.** `create_note` wrote into a hole: nothing
  listed notes and search did not look inside them. Notes are searchable now
  (behind `crm.read`, with a snippet around the hit), `list_notes` returns
  them per record with bodies rendered as text, and `update_note` rewrites
  one - which is how a card whose facts have moved into custom fields gets
  trimmed, and how a stale card stops contradicting the note next to it.
- **Reach the knowledge base.** `create_kb_page` needed a `spaceId` no tool
  produced. `list_kb_spaces`, `list_kb_pages`, `get_kb_page` (body as text)
  and `update_kb_page` close that loop the same way.
- **Assign an owner.** `create_company` and `create_deal` take an `ownerId`,
  and `list_users` resolves the ids for it - the field existed on both
  endpoints with no way to fill it.
- `create_company` refuses a name or domain that already exists, naming the
  record to update instead, since a re-run of an import is exactly how it
  gets called twice.
- `move_deal` takes `customFields`, so a lost deal's structured reason is
  written with the move rather than drifting from the free-text one.
- `update_custom_field` can retire a definition with `deprecated` - the flag
  the model already had and nothing could set.

## Also in this release

- `GET /contacts/:id`. Companies and deals read back on an id; contacts only
  came out of a per-company list, so a caller holding a contact id had to
  know its company first.
- Reading a project's repository bindings and git automation rules dropped
  to viewer level. The panel renders them read-only for non-managers, so
  gating the read on project admin only made it 404 to its own readers.
- Leave types are readable by anyone signed in - it is the vocabulary of the
  request form, and filing leave does not need `people.read`. Defining them
  still does.
