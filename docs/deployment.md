# ordi – Deployment guide (production)

Цільова інфраструктура за ТЗ – **self-hosted на Dokploy** (Docker), зовнішні
залежності лише SMTP і S3-сумісне сховище. Той самий стек розгортається й на
будь-якому VPS через `docker compose`.

## 0. Що деплоїться

| Сервіс | Образ | Порт | Примітка |
|---|---|---|---|
| `db` | postgres:16-alpine | 5432 | том `db_data`; PITR – див. operations.md |
| `minio` | quay.io/minio/minio | 9000/9001 | опційно – замініть на R2/S3 |
| `api` | `ghcr.io/romirom11/ordi` | 3000 | **весь застосунок**: міграції, API, воркери і зібраний веб |

Образ `api` публікується автоматично на кожному релізі
(`.github/workflows/image.yml`, `linux/amd64`): `docker pull
ghcr.io/romirom11/ordi:latest` працює без жодної автентифікації в GitHub, а
кожен реліз має й тег версії (`ghcr.io/romirom11/ordi:1.34.0`) – саме на
нього закріплюйтесь (`ORDI_VERSION=1.34.0` в env) і на нього відкочуєтесь.
Сервер нічого не збирає: `pnpm install` і збірка веба відбуваються один раз
у CI. Збирати образ локально потрібно лише для форка чи зміни
`docker/Dockerfile.api` – для цього є оверлей `docker-compose.build.yml`.

З v1.6.0 **один контейнер – це весь застосунок**: `api` сам віддає SPA,
`/api/*`, SSE і OAuth-дискавері для MCP (`/.well-known/*`). Окремого
веб-сервера немає і налаштовувати між контейнерами нічого. (Старий
nginx-образ `docker/Dockerfile.web` – deprecated з v1.6.0 – видалено; якщо ви
досі пінили його, див. крок 3 нижче.)

## 1. Варіант A – Dokploy (рекомендований)

1. **Створіть проєкт → Compose** і вкажіть цей репозиторій та
   **`docker-compose.prod.yml`**. Dokploy нічого не збирає: сервіс `api`
   тягне опублікований образ `ghcr.io/romirom11/ordi` (`pull_policy:
   always`, тож кожен Redeploy у панелі ставить актуальний образ тега).
   Без `ORDI_VERSION` це `latest`; для закріплення на релізі задайте
   `ORDI_VERSION=1.34.0` в Environment.
   `docker-compose.yml` у корені – для локального запуску: він прибиває
   значення до `localhost` і публікує порти на хост.
2. **Environment** (мінімум для прод):
   ```bash
   AUTH_SECRET=$(openssl rand -hex 32)
   ENCRYPTION_KEY=$(openssl rand -hex 32)     # AES-256-GCM для git-креденшелів
   AGENT_WORKER_SECRET=$(openssl rand -hex 32) # api ↔ agent-worker, §3b
   SMTP_URL=smtps://user:pass@smtp.example.com:465
   ```
   і відредагуйте в compose (або винесіть у env) значення під ваш домен:
   `APP_URL=https://ordi.example.com`, `CORS_ORIGINS=https://ordi.example.com,tauri://localhost`.
   `APP_URL` потрапляє в email-и та публічні лінки PDF – він мусить бути
   реальним доменом.
3. **Домен + HTTPS**: у Dokploy привʼяжіть домен до сервісу **`api`**
   (**порт 3000**, Path `/`) – Traefik видасть сертифікат. Більше жодних
   правил маршрутизації: цей самий сервіс віддає і сайт, і `/api/*` (у т.ч.
   SSE), і `/.well-known/*` для MCP-конекторів.
   Git-вебхуки: `https://ordi.example.com/api/v1/integrations/git/<provider>/webhook`.
   Для GitHub цей вебхук реєструється автоматично, якщо підключення створене
   через GitHub App (Налаштування → Інтеграції → Create GitHub App); вручну
   його треба прописувати лише для GitLab/Gitea або legacy-підключень токеном.

   **Оновлюєтесь із версії до v1.6.0?** Переведіть домен із сервісу `web`
   (порт 80) на `api` (порт 3000), видаліть сервіс `web` і будь-який ручний
   маунт nginx-конфіга, який ви для нього робили. Жодних нових env.
4. **Сховище файлів** – два шляхи, обидва через змінні:
   - *Зовнішній S3/R2*: задайте `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`,
     `S3_SECRET_KEY`, `S3_REGION`.
   - *Вбудований MinIO*: додайте `COMPOSE_PROFILES=minio`,
     `S3_ENDPOINT=http://ordi-minio:9000` і ту саму пару
     `S3_ACCESS_KEY`/`S3_SECRET_KEY` – вона ж стає root-креденшелами MinIO,
     тож api і сховище фізично не можуть розійтися. Бакет створюється
     автоматично при першому старті (`minio-init`). Адреса саме
     `ordi-minio`, не `minio`: на спільній мережі PaaS (Dokploy/Coolify)
     api бачить чужі контейнери, і генеричний аліас `minio` може
     зарезолвитись у сусідній проєкт.

   Сховище назовні не виставляється взагалі: браузер вантажить і читає файли
   через API, а вже API ходить у бакет по внутрішній мережі. MinIO не потрібні
   ні публічний домен, ні CORS, ні консоль.
5. **Перший запуск** – сід ролей/власника (одноразово):
   ```bash
   docker compose exec api \
     env SEED_OWNER_EMAIL=you@agency.com SEED_OWNER_PASSWORD='строгий-пароль' \
     pnpm --filter @ordi/api seed
   ```
   Далі логін під цим власником; демо-користувачам (`member@ordi.local`)
   змініть пароль або деактивуйте їх у Settings → Users.
6. **Health checks**: `GET /healthz` (liveness) і `GET /readyz` (readiness,
   перевіряє БД) на сервісі `api` – додайте їх у Dokploy/моніторинг.

## 2. Варіант B – голий VPS

```bash
mkdir ordi && cd ordi
curl -fsSLO https://raw.githubusercontent.com/romirom11/ordi/master/docker-compose.prod.yml
# .env: POSTGRES_PASSWORD, AUTH_SECRET, ENCRYPTION_KEY, AGENT_WORKER_SECRET, APP_URL, SMTP_URL, S3_*
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml exec api pnpm --filter @ordi/api seed   # одноразово
```
Клонувати репозиторій не потрібно – образ уже зібраний. Або без S3 і
домену, для проби на `localhost:8080`: той самий рецепт з `docker-compose.yml`
із README.
Далі поставте перед `api` (хост-порт 8080 або 3000) будь-який TLS-термінатор
(Caddy/Traefik/nginx) – він проксіює все на один порт, без окремих правил.

## 3. Оновлення (нові релізи)

Стандартний цикл – без збірки на сервері:

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

На Dokploy те саме робить кнопка **Redeploy** (образ тягнеться при кожному
`up`). Закріплені на версії (`ORDI_VERSION=1.34.0`)? Змініть значення на
нову версію і повторіть. Відкат – та сама операція з попередньою версією:
`ORDI_VERSION=1.33.1 docker compose -f docker-compose.prod.yml up -d`. Теги
кожного релізу: `1.34.0`, `1.34`, `1`, `latest`.

Міграції **адитивні** і запускаються автоматично в entrypoint API-контейнера
перед стартом сервера – окремих кроків немає. Rollback безпечний: попередній
образ працює зі схемою нового (руйнівних DDL немає). Zero-downtime на одному
хості не гарантується (кілька секунд рестарту).

Сервер повідомляє свою версію у `GET /healthz`, і застосунок звіряє її зі
своєю:

- **Веб**: після оновлення сервера відкриті вкладки показують банер
  «Доступна нова версія» з кнопкою перезавантаження.
- **Десктоп** оновлюється сам через GitHub-релізи, але UI він возить із собою,
  тому важлива і зворотна перевірка: якщо сервер *старіший* за застосунок,
  зʼявляється попередження з посиланням сюди. Побачили його – час зробити
  `docker compose pull && docker compose up -d` на сервері.
- **Settings** показує поточну версію внизу навігації, а адміністраторам – і
  посилання на новіший реліз, щойно він виходить.

## 3a. Пошта

Один SMTP-транспорт обслуговує запрошення, надсилання рахунків і пропозицій
(PDF + публічне посилання), нагадування про оплату, відповіді на заявки з
Intake і дублювання сповіщень. Мова листа береться з локалі отримувача (свої
користувачі) або з мови документа (клієнти) – uk/en. Без налаштованого SMTP
листи **не надсилаються**, а лише пишуться в лог.

Інтерактивне надсилання документа виконується одразу, щоб користувач отримав
успіх або помилку в тому самому запиті. Системні сповіщення, payment reminders
і sales-work digest спочатку потрапляють у `email_deliveries`: вбудований worker
у тому самому `api`-контейнері відправляє їх у фоні, повторює після помилок і
відновлює покинуті claims після рестарту. Окремий queue-сервіс або процес
налаштовувати не потрібно. Моніторинг pending/dead/stale rows описаний у
[`docs/operations.md`](operations.md).

**Де налаштовувати.** Найпростіше – у застосунку: **Налаштування →
Інтеграції → Пошта**. Там же кнопки «Перевірити зʼєднання» (чи взагалі
відкривається порт) і «Надіслати тестовий лист» (наскрізна перевірка
доставки). Пароль зберігається зашифрованим і назад клієнту не віддається.

`SMTP_URL` і `SMTP_FROM` у `.env` лишаються запасним варіантом: якщо в UI
нічого не задано, беруться вони. Значення з UI мають пріоритет, а на екрані
видно, звідки взято чинні налаштування.

> Найчастіша причина, чому пошта не йде, – **хостинг блокує вихідні
> SMTP-порти** (25/465/587). Тоді «Перевірити зʼєднання» покаже `ETIMEDOUT`.
> Просіть провайдера відкрити порти або беріть поштовий сервіс з API поверх
> HTTPS.

**Перевірка перед прод.** У `docker-compose.yml` є `mailpit`: задайте
`SMTP_URL=smtp://mailpit:1025` і відкрийте http://localhost:8025 – там видно
кожен лист рівно таким, яким його отримає клієнт (HTML, текстова версія,
вкладення).

**Доставність.** Опублікуйте DNS-записи для домену, з якого шлете, інакше
листи потраплятимуть у спам або відхилятимуться:

| Запис | Приклад | Навіщо |
| --- | --- | --- |
| SPF | `v=spf1 include:_spf.your-provider.com -all` | дозволяє серверам провайдера слати від імені домену |
| DKIM | CNAME/TXT з панелі SMTP-провайдера | криптопідпис листа; провайдер видає селектор |
| DMARC | `v=DMARC1; p=quarantine; rua=mailto:dmarc@your-domain` | політика для листів, що не пройшли SPF/DKIM |

Домен у `SMTP_FROM` має збігатися з доменом, для якого налаштовані SPF/DKIM
(інакше DMARC не зійдеться). Дефолтний `no-reply@ordi.local` для прод не
годиться. Обробки повернень (bounce) і списку відписок поки немає – за
репутацією домену слідкуйте в панелі провайдера.

## 3b. Агенти (Claude Code)

Агент-співробітник – це користувач з `actor_type = 'agent'`: йому призначають
задачу так само, як людині, а платформа запускає Claude Code проти
репозиторію проєкту і доводить роботу до pull request. Виконує запуски
**окремий сервіс `agent-worker`** – він є в обох compose-файлах і стартує
разом з усім, налаштовувати його не треба: той самий образ, інша команда,
а з оточення – лише адреса API і спільний секрет `AGENT_WORKER_SECRET`. Це
єдине місце в ordi, де виконується код, написаний моделлю, тому в цьому
контейнері немає ні `DATABASE_URL`, ні `ENCRYPTION_KEY`, ні `AUTH_SECRET`
(деталі нижче). В образі для цього стоїть `git`, а сам рантайм Claude Code
приїжджає разом із SDK (`@anthropic-ai/claude-agent-sdk`); збірка образу
падає, якщо бінарник не резолвиться, тож «встановилось, але не працює» тут
не буває.

**Змінні оточення**

| Змінна | Де | Дефолт | Навіщо |
|---|---|---|---|
| `AGENT_WORKER_SECRET` | `api` і `agent-worker` | – (обовʼязкова у `docker-compose.prod.yml`) | спільний секрет, будь-який випадковий рядок (`openssl rand -hex 32`); ним воркер автентифікується на `/api/v1/agent-worker/*`. Без нього API відповідає на ці маршрути 503 |
| `ORDI_API_URL` | `agent-worker` | `http://ordi-api:3000` у compose | адреса API з середини мережі; compose уже задає її |
| `AGENT_WORKER_CONCURRENCY` | `agent-worker` | `2` | скільки запусків цей процес тримає одночасно; на агента є ще власний ліміт `concurrency` |
| `AGENT_WORK_DIR` | `agent-worker` | `/data/agent-work` | `tasks/<taskId>/checkout` – свіжий клон на кожен запуск, видаляється після завершення; `tasks/<taskId>/harness` – домівка Claude Code зі стенограмою сесії, лишається, щоб follow-up і Retry продовжили ту саму розмову; прибирається через 30 днів після останнього запуску задачі |
| `AGENT_WORKER_ENABLED` | `api` | `0` у compose (`1`, якщо змінна не задана) | вбудований воркер усередині процесу API. У compose він вимкнений, бо запуски виконує `agent-worker`; `1` потрібна лише для запуску без compose (`pnpm dev`) або якщо ви свідомо хочете все в одному контейнері |
| `ANTHROPIC_API_KEY` | `api` | – | запасне джерело **тільки для API-ключа**, щоб PaaS міг налаштувати Claude без заходу в UI; у Налаштуваннях → Агенти воно видно як read-only картку. Лишається на API: воркер отримує доступ на кожен запуск окремо |

**Том для робочих копій.** Обидва compose-файли монтують іменований том
`agent_work:/data/agent-work` **сервісу `agent-worker`** (API він не
потрібен). Під час запуску там лежить повний клон репозиторію, тож розмір
тому беріть як `AGENT_WORKER_CONCURRENCY` × розмір репозиторію з запасом;
між запусками лишаються тільки стенограми сесій (мегабайти на задачу, 30
днів). Том має бути один і той самий для всіх воркерів, інакше Retry на
іншому хості не знайде сесію і почне задачу з гілки заново (див.
[`docs/operations.md`](operations.md)).

**Підключення Claude.** **Налаштування → Агенти** – одна робоча область, один
доступ на всіх агентів. Два рівноправні варіанти:

- **Підписка.** На своїй машині виконайте `claude setup-token` (потрібен план
  Pro/Max/Team/Enterprise) і вставте отриманий токен – він живе рік, ordi
  нагадає власникам `agents.manage` за 14 днів до кінця.
- **API-ключ Anthropic.** Той самий діалог, інший тип.

Секрет шифрується AES-GCM (`ENCRYPTION_KEY`) і назад клієнту не віддається;
на картці видно, **хто підключив** і коли, бо запуски агентів витрачають саме
його план. Кнопка «Перевірити» робить мінімальний запит і записує результат.

**GitHub App: нові права.** Маніфест тепер просить `contents: write` і
`pull_requests: write` – агент пушить свою гілку і відкриває PR
інсталяційним токеном. Нові застосунки створюються вже з ними; **існуючу
інсталяцію GitHub не розширює сам** – власник організації має прийняти нові
права (GitHub надішле запит, а в Налаштування → Інтеграції видно стан). Доки
він цього не зробив, читання й вебхуки працюють, а пуш агента падає.

**MCP-конектори.** Конектори підключаються в **Налаштування → Конектори**
(право `integrations.manage`), а вже на картці агента позначається, які саме
йому дозволені. Агент ходить у них не напряму, а через шлюз ordi
(`POST /api/v1/mcp-connectors/:slug/mcp`), тож жоден upstream-секрет до
процесу агента не потрапляє. Для конекторів з OAuth потрібен публічно
доступний callback:

```
APP_URL/api/v1/mcp-connectors/oauth/callback
```

Він має відкриватися **у браузері адміністратора**, який дає згоду, тобто
`APP_URL` знову мусить бути реальним https-доменом (як і для MCP-дискавері,
§5). Локальний інстанс без публічного домену такі конектори не підключить.

**Права.** Все, що стосується агентів – доступ Claude, створення агентів,
ліміти, політика призначення, список дозволених конекторів, скасування
запусків – під новим правом `agents.manage`. Owner і Admin отримують його
автоматично (міграція `0035_ai_agents.sql` бекфілить його в ці дві ролі);
будь-якій кастомній ролі його можна видати в матриці ролей. Сам агент
працює під звичайною роллю – пресет `Agent` (projects.read, projects.write,
kb.read) – і бачить лише ті проєкти, де він учасник.

**Чому воркер – окремий контейнер.** Запуск агента – єдине місце в ordi, де
виконується код, написаний моделлю. Дочірній процес і так отримує
перебудоване оточення без `DATABASE_URL`, `ENCRYPTION_KEY`, `AUTH_SECRET`,
S3 і SMTP, токен запуску відкликається наприкінці, є списки дозволених і
заборонених інструментів – але радіус ураження втечі з цього процесу
дорівнює контейнеру, в якому він живе, а в `api`-контейнері лежить усе.

Тому воркер працює **як окремий процес без бази**: він говорить з API лише
по HTTP (`/api/v1/agent-worker/*`) і тримає тільки те, що потрібно одному
запуску – доступ Claude, токен репозиторію і власний токен запуску, кожен з
яких обмежений або відкликається. Жодного `DATABASE_URL`, `ENCRYPTION_KEY`
чи `AUTH_SECRET` у воркера бути не повинно – він і не попросить, а якщо PaaS
підсуне їх у кожен контейнер проєкту, воркер напише про це попередження в
лог. Запуски беруться з черги через `FOR UPDATE SKIP LOCKED` на боці API,
тож двічі один запуск не виконається, навіть якщо помилково увімкнути
`AGENT_WORKER_ENABLED=1` на API. Воркеру можна дати власні ліміти
CPU/памʼяті, окрему мережу (йому потрібні лише API, GitHub і Anthropic), а з
часом і власну віртуальну машину – API про це не знає. Стан воркера видно в
**Налаштування → Агенти** (heartbeat кожні 15 секунд).

**Оновлюєтесь із v1.33 або старішої?** Додайте `AGENT_WORKER_SECRET` в
оточення – без нього `docker-compose.prod.yml` тепер не піднімається. Якщо
ви вже розкоментували `agent-worker` самі, приберіть свою копію: сервіс
тепер у файлі. Якщо `api` мав `AGENT_WORKER_ENABLED=1` в env – видаліть,
щоб він не брав запуски поруч із воркером. Том `agent_work` той самий, тож
стенограми сесій нікуди не діваються.

**Все в одному контейнері.** Не рекомендовано, але можливо: на `api`
поставте `AGENT_WORKER_ENABLED=1`, змонтуйте йому `agent_work:/data/agent-work`
і піднімайте з `--scale agent-worker=0`. Воркер усередині `api` викликає ті
самі функції напряму.

## 4. Обовʼязково для прод (чекліст)

- [ ] `AUTH_SECRET`, `ENCRYPTION_KEY` і `AGENT_WORKER_SECRET` – випадкові
      32-байтові, тільки в env.
- [ ] `APP_URL`/`CORS_ORIGINS` = реальний https-домен.
- [ ] SMTP налаштований (без нього листи лише логуються), `SMTP_FROM` на
      вашому домені, SPF/DKIM/DMARC опубліковані – див. §3a.
- [ ] S3/MinIO з бакетом – інакше вкладення недоступні (API чесно відповідає
      «Object storage is not configured»). Назовні сховище не виставляється –
      файли ходять через API (див. §4).
- [ ] **Бекапи**: PITR через WAL-G (RPO ≤ 5 хв) + реплікація бакета вкладень –
      покрокова інструкція і runbook відновлення: `docs/operations.md`.
- [ ] Моніторинг: `/healthz`, `/readyz`, глибина dead-letter, лаг WAL –
      SQL-запити для алертів у `docs/operations.md` §5.
- [ ] (Опційно) **Агенти**: підключений Claude, том `agent_work` у сервісу
      `agent-worker`, прийняті нові права GitHub App – §3b. Якщо агентів не
      буде, сервіс можна не піднімати (`--scale agent-worker=0`); без
      підключеного Claude він і так простоює.

- [ ] (Опційно) `SENTRY_DSN` (API) і `VITE_SENTRY_DSN` (web, задається на
      етапі збірки web-образу) для звітів про помилки.
- [ ] (Опційно) **Typst** для брендованого PDF: додайте в `docker/Dockerfile.api`
      установку бінарника (`typst` у PATH). Без нього рахунки генеруються
      вбудованим простим рендером – валідний PDF, але без бренд-верстки.

## 5. Десктоп і MCP

- **Образ**: той самий тег запускає `.github/workflows/image.yml` – збірка
  `docker/Dockerfile.api` (`linux/amd64`), пуш у `ghcr.io/romirom11/ordi` з
  тегами `<версія>`, `<major>.<minor>`, `<major>`, `latest`, `sha-<коміт>`, і
  перевірка, що образ тягнеться **без автентифікації** та відповідає на
  `/healthz` своєю версією. Зелений воркфлоу означає саме «pull працює»:
  якщо пакет виявиться приватним, крок анонімного pull падає з
  інструкцією, де зробити його публічним. Запуск
  воркфлоу вручну на гілці публікує лише `sha-<коміт>` – прев’ю-образ, що
  ніколи не зачіпає `latest`.
- **Desktop**: пуш тега `v*` у GitHub запускає `.github/workflows/desktop.yml`
  (macOS universal / Windows msi / Linux AppImage+deb через tauri-action).
  Для підписаного апдейтера задайте секрети `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)`.
  Перший запуск застосунку питає URL інстансу – ваш `https://ordi.example.com`.
- **MCP-агент**: створіть API-токен у Профілі (скоуп ⊆ вашої ролі) і запускайте
  `pnpm --filter @ordi/mcp start` з `ORDI_API_URL=https://ordi.example.com` та
  `ORDI_API_TOKEN=<токен>` на машині агента.
- **MCP-конектор (Claude, Cursor) через OAuth**: клієнт вказує на
  `https://ordi.example.com/api/v1/mcp`, далі все робиться самим клієнтом –
  дискавері, реєстрація, логін, згода. Вимоги до вашого проксі:
  - **`Host` і `X-Forwarded-Proto` мають доходити до API.** Дискавері віддає
    абсолютні URL і будує їх із цих заголовків. Якщо проксі їх губить, клієнт
    отримає адресу, якої не існує назовні, і скаже щось на кшталт «couldn't
    register with the sign-in service». Якщо домен дивиться прямо на `api`,
    робити нічого не треба; для власного проксі перевірте вручну:
    ```
    curl -s https://ordi.example.com/.well-known/oauth-authorization-server
    ```
    `issuer` і `registration_endpoint` мусять бути на вашому публічному
    домені, а не на `localhost` чи `api:3000`.
  - **Публічний HTTPS.** Реєстрацію робить сервер клієнта, а не ваш браузер,
    тож інстанс має бути доступним з інтернету по https. Для інстансу в
    локальній мережі OAuth-конектор не спрацює – там лишається токен.
  - `APP_URL` тепер потрібен лише як запасний варіант (і для email-посилань),
    але тримайте його в актуальному стані.
