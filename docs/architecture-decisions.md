# ordi — Architecture decisions & improvements

This document records implementation decisions and deviations/refinements made
while building ordi from `docs/prd.md`. The PRD is the product contract; this
file is the engineering log of *how* it was realized and *why* a few things were
adjusted. Every decision preserves the PRD's architectural invariants (modular
monolith, one API contract, RBAC on the backend, event outbox, additive schema).

## 1. Monorepo & module resolution

- **pnpm workspaces + Turborepo** as specified. Packages: `@ordi/shared`,
  `@ordi/db`, `@ordi/mcp`; apps: `@ordi/api`, `@ordi/web`, `@ordi/desktop`.
- **Extensionless relative imports + `moduleResolution: Bundler`.** The initial
  code used explicit `.js` extensions (Node16/NodeNext style), but `drizzle-kit`
  loads the schema through esbuild and cannot remap `./core.js` → `./core.ts`,
  which broke migration generation. Decision: use extensionless relative imports
  repo-wide. Consequence: the runtime is **tsx** (dev + container) and bundlers
  (Vite for web). This keeps a single, consistent import style and unblocks
  `drizzle-kit generate`. The API container runs `tsx src/server.ts` — acceptable
  at this scale and avoids a bundler in the critical path; a future `tsup` bundle
  step maps 1:1 if a pure-`node dist` image is ever needed.

## 2. Shared pure-calc modules (single source of truth)

The PRD requires unit tests for money, cost/profitability, aging, burndown,
leave balances, git-mention parsing, the RBAC resolver, and the redaction
serializer (§20). These are implemented as **pure functions in `@ordi/shared`
(`src/calc/*`)** so the API, web, MCP, and tests all consume one implementation:

- `calc/money.ts` — invoice/quote totals (integer-cents to avoid float drift),
  partial-payment state, overpayment guard.
- `calc/cost.ts` — versioned compensation lookup, hourly cost rate, overhead per
  hour, project/client profitability, utilization.
- `calc/aging.ts`, `calc/leave.ts`, `calc/git-mentions.ts`, `calc/fractional.ts`,
  `calc/rbac.ts`, `calc/redaction.ts`.

39 unit tests cover these. This is a **refinement over the PRD**, which located
some of this logic in domain services; centralizing it removes drift risk and
makes the invariants directly testable.

## 3. Database

- **ULID PKs**, `created_at/updated_at/created_by`, `version`, `deleted_at`,
  `custom_fields` as specified (§5.2).
- **Optimistic locking**: a generic `ordi_bump_version()` trigger increments
  `version` on every `UPDATE` for every table that has the column (installed by a
  DO-loop over `information_schema`). Services also add `version` to the `WHERE`
  clause so a concurrent update affects 0 rows → 409. `updated_at` is never used
  for concurrency (a matching trigger keeps it fresh for display only).
- **Per-project task numbering**: rather than a counter column on `projects`
  (which the version trigger would bump on every task insert, causing spurious
  project 409s), numbering uses a dedicated `task_number_counters` table updated
  atomically via `INSERT … ON CONFLICT … RETURNING` inside a `BEFORE INSERT`
  trigger. This is a **deliberate improvement** over a naive project counter.
- **FTS**: generated `tsvector` columns (`to_tsvector`/`jsonb_to_tsvector` with a
  literal `simple` config, which are immutable) + GIN indexes on companies,
  contacts, projects, tasks, kb_pages; trigram indexes on invoice/quote numbers
  (§5.2, §14.2). Tiptap JSON bodies are indexed via `jsonb_to_tsvector`.
- **Custom fields** (§5.5): level-1 GIN index on each `custom_fields` column;
  level-2 point B-tree expression indexes created on demand when a definition is
  flagged `indexed` (`core/customfields.ts`). Filters are structured
  `{field_key, op, value}`, validated op-under-type against the registry, and
  compiled to parameterized JSONB predicates — never raw client SQL. Sorting
  projects to a typed cast and is restricted to number/date/select/text.
- Migrations are generated by `drizzle-kit`; `migrate.ts` applies them then
  `triggers.sql` (idempotent). Additive-only, run as a separate deploy step (§19.2).

## 4. RBAC & access

- Two-level model exactly as §4: capability permissions (role → set, cached
  in-process, invalidated by the `role.updated` event) + resource membership
  (project/space). `core/rbac.ts` `guard(permission)` is declarative per route.
- API tokens carry a scope that is intersected with the owner's role permissions
  at request time (`effectivePermissions`), and a `read_only` flag blocks write
  permissions. Token scope wider than the owner's role is rejected at creation.
- **Resource-scoped reads are membership-gated, not permission-guarded.**
  Projects, tasks, KB pages/comments, and a user's own time are read via
  `requireAuth` + `assertProject`/`assertSpace`/`accessibleProjectIds` rather than
  a `guard('projects.read')`. Reason: a **Guest** has no global `projects.read`
  but must see the projects they are a member of (§4.3, §17.2). Workspace-level
  configuration writes still use `guard(...)`. This is the correct reading of the
  PRD's dual-level rule (`hasPermission AND (unrestricted OR isMember)`).
- 404 (not 403) is returned for resources outside the caller's access, to avoid
  leaking existence (§15.1, §19.1).

## 5. Events & realtime

- **Outbox** (`events` table) written in the same transaction as the change
  (§3.3). A **polling relay** (`workers/relay.ts`) reads unpublished events in
  `occurred_at` order and dispatches to idempotent consumers (SSE, notifications,
  git automations, outbound webhooks). Dedup via `processed_events`. Per-consumer
  **retry with exponential backoff** (10s→2h) and **dead-letter** after 5
  attempts; an event is marked published only when every consumer reaches a
  terminal state, so a poison event never blocks the queue.
  - Decision: the outbox relay is a bespoke in-process loop rather than pg-boss.
    pg-boss doesn't give strict per-aggregate ordering, and the single-threaded
    relay processing in `occurred_at` order yields correct ordering trivially at
    this scale. **pg-boss is used for scheduled cron jobs** (recurring
    tasks/invoices, reminders, burndown snapshots, quote expiry) with an interval
    fallback if pg-boss is unavailable. All jobs are idempotent.
- **SSE** `/api/v1/stream` filters messages by the subscriber's accessible
  projects / user id (`core/events.ts` broadcaster). The `EventBroadcaster`
  abstraction is where a Redis pub/sub fan-out would slot in for multi-replica.

## 6. Money, PDF, email, storage

- All monetary math flows through `@ordi/shared/calc/money`. Numeric columns are
  Postgres `NUMERIC(14,2)` and surface as strings through Drizzle; services cast
  explicitly.
- **PDF** (`lib/pdf.ts`): renders via the **Typst** CLI when present (branded
  template), else a dependency-free minimal PDF writer, so the endpoint always
  returns a valid PDF even without Typst installed.
- **Email** (`lib/email.ts`): Nodemailer + SMTP; without SMTP configured it logs
  (dev) instead of sending. **S3** (`lib/s3.ts`): presigned upload/download;
  without an endpoint it returns a `local://` stub so uploads degrade gracefully.
- **Git credentials** are encrypted at rest with AES-256-GCM (`lib/crypto.ts`).
  Secrets/tokens are never returned by any endpoint and never enter the audit
  diff (redaction serializer excludes them entirely).

## 7. Audit & sensitivity

- Every mutation writes an immutable `activity_log` row with a **redacted diff**
  (`core/activity.ts` + `calc/redaction.ts`): sensitive fields (compensation,
  persona, salary ranges) record the *fact* of change without the value; secrets
  are excluded entirely. HR/compensation records are tagged `sensitivity:
  sensitive`, hidden from the general audit feed unless the viewer holds
  `people.read_sensitive`/`read_compensation`, and reads of compensation are
  themselves logged (who viewed salary).

## 8. Domain module layout

Each domain lives in `apps/api/src/domains/<domain>/` with `routes.ts` (thin:
guard → validate → service) and `service.ts` (business logic), matching §3.2. No
domain imports another domain's service; interaction is via FK, the event bus,
and shared read contracts. Public/unauthenticated surfaces (invoice/quote/portal/
intake/careers pages, git webhooks) live in a dedicated `public` module.

## 9. Deliberate scope calls for this build

- The full desktop (Tauri) shell is scaffolded (config + guide) rather than
  producing native binaries in CI here; it wraps `apps/web` unchanged per §18.
- IMAP intake polling and the S3/SMTP/Typst integrations are wired behind
  interfaces and degrade to safe no-ops when unconfigured, so the system runs
  end-to-end in a bare environment while remaining production-ready when the
  external services are provided.
- All §22 compromises are respected (no online payments, no accounting/e-invoicing,
  no automation builder, permission-level finance/CRM access, token portal, etc.).

## 10. Gap-closure wave (post-1.0 hardening)

After the initial full implementation, the remaining PRD deltas were closed:

- **Task views**: Calendar, Timeline (pure-CSS Gantt with overdue shading and a
  today line) and Spreadsheet (inline cell editing + bulk column edit) joined
  List/Board; the active view persists per project; saved views (personal/shared)
  get a chips bar. No chart library — deliberate, keeps the bundle small.
- **Rich text**: real Tiptap editor (StarterKit, links, task lists, placeholder,
  @mentions with a dependency-free suggestion dropdown) + a recursive read-only
  renderer. Mentions store tiptap-standard `attrs.id`, which the KB backlink
  extractor already consumes. Mention directory comes from a new
  `GET /users/lookup` (id/name/avatar only — no emails/roles), available to any
  authenticated user so mentions are not admin-only.
- **Realtime**: the SPA subscribes to `/api/v1/stream` (`lib/sse.ts`) and maps
  event families to TanStack Query invalidations with reconnect/backoff.
- **Keyboard**: ⌘K palette, `C` quick-create (with `!priority` quick-syntax),
  `T` stop timer, `G`-chords (`G D/P/C/F/K/T/M`) for navigation.
- **i18n**: key-based uk/en dictionaries (`lib/i18n.tsx`); locale from the user
  profile, Intl for dates/money; public pages guess locale pre-auth. PDF
  labels are localized per document (uk/en) in the Typst template and fallback.
- **OpenAPI**: a static OpenAPI 3.1 doc generated from the shared Zod schemas
  (zod-to-json-schema) served at `/api/docs` — chosen over migrating every route
  to hono-openapi (invasive) while still giving a typed public contract.
- **TOTP**: setup/enable/disable endpoints + profile UI (otpauth URL + secret).
- **DLQ admin**: `/dlq` list + replay + deliberate reprocess (clears
  processed_events), surfaced in Settings → Event queue; audit feed panel too.
- **CSV**: import (companies/contacts/tasks, dry-run with per-line errors,
  transactional apply) and export (companies/contacts/tasks/invoices/time) with
  a dependency-free CSV codec.
- **IMAP intake**: `workers/imap.ts` polls configured project mailboxes
  (ImapFlow + mailparser) every 10 minutes, mapping unseen mail to intake items;
  per-mailbox failures are isolated.
- **Observability**: pino stays; a dependency-free Sentry reporter (store-API
  envelope via fetch) activates on `SENTRY_DSN` / `VITE_SENTRY_DSN` — swappable
  for the full SDK behind the same `captureException`.
- **Ops**: `docs/operations.md` — PITR (WAL-G) setup meeting RPO ≤ 5 min,
  rehearsed restore runbook for RTO ≤ 1 h, monitoring queries (DLQ depth, WAL
  lag, outbox lag), sensitive-audit retention purge.
- **Desktop**: CI workflow (`desktop.yml`) builds macOS universal / Windows msi /
  Linux AppImage+deb via tauri-action on version tags — binaries are a CI
  artifact by design; the container environment lacks GTK/WebKit dev libs.

## 11. Testing

- Unit (Vitest) in `@ordi/shared` for all pure calc (money, cost, aging, leave,
  git, RBAC resolver, redaction).
- API integration tests (`apps/api/src/**/*.test.ts`) cover the RBAC permission
  matrix, sensitive-data isolation, version locking, internal-project rules, and
  outbox idempotency/DLQ — generated where possible from the permission catalog so
  a new permission without a test fails CI (§20).

## 11. OpenAPI publication (§15.1)

The `/api/docs` contract is a static OpenAPI 3.1 document built at module load
in `apps/api/src/domains/core/openapi.ts` from the shared Zod input schemas via
`zod-to-json-schema`, rather than per-route `hono-openapi` decoration: routes
stay thin (guard → validate → service) and the doc adds an `x-permission`
extension per operation so MCP/external integrations can see the required
capability. `/api/docs/openapi.json` serves the raw spec; `/api/docs` serves a
dependency-free HTML browser over it. Responses are intentionally loose
(generic envelope) — handlers remain the source of truth for response shapes.
